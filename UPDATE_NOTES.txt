- On the dedicated server, the HTTP method of a request now reaches plugins correctly, so web panels of server plugins can POST again. Before, every request reached plugins as an unknown method and a plugin that only accepts POST rejected its own panel. The method comes from the version object map row for the server game build (CL-127004); a server build without that row keeps the old behaviour and ModLoader.log says so.
- When a game update changed some of the game classes the mod loader's start check reads, but none that every plugin depends on, a plugin that does not take its game data from the version object map was refused. It is now still loaded if it names the game build it was compiled for and that is the build running, since its game data is that build's. If a class every plugin depends on changed, or the game's ProcessEvent moved, all plugins still stay off. A plugin that names no build or another build, and has not moved to the version map, is refused as before
- The mod loader's client build now takes its game classes from the CL-130045 game files and still runs on CL-127004 with the same files. The version object map keeps the rows for both builds, and the two members that sit at a different place on the two builds (a crafter's crafting component and the enviro wave timer's actor) are read per build, so a CL-127004 game is not mistaken for a changed layout. The dedicated server is unchanged and stays on CL-127004
- The dedicated server's mod loader now carries a built-in table of version object map rows for the one server game build it was written for: function addresses, the game's data globals, and member offsets and struct sizes read from the server's own game files. A plugin that asks for a version map key, member or struct size gets the row on that exe, matched by its game build and the exe's own stamp and size, and on any other server exe the table stays off and the plugin runs on its own patterns and rows as before. Field, size and absent-member lookups and the class bound on native members read the same table, and the client's version map is unchanged
- The dedicated server now hands plugins the same Game-SDK globals as the client (GObjects, GNames, FName::AppendString and GWorld) when the version object map serves the running server build, and its table has the row for FName::AppendString. On any other server exe nothing changes: the SDK keeps its compiled offsets and plugins are handed none
- The dedicated server's mod loader can now download, check and keep its own signed version object map file (version-map-server.v1.txt, kept as ModLoader\version-map-server.v1.cache), the way the client does; the release builds carry the address for it, and a server build made without one fetches nothing and says so in ModLoader.log. A client never reads the server's file and a server never reads the client's, and each refuses the other's with a clear log line. A server game build that only that file lists is served from it, and only when the game build number, the exe's time stamp and its image size all match a build line in it; the server's built-in table still wins on the exe it was measured on. Plugins that take their game data from the version object map then run on that build, and a build whose loader values or game globals are not all found starts without plugins. Nothing is published for it yet, so a server still runs only the game build it was made for until a server file is released
