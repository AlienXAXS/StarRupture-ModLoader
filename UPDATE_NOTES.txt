- A plugin's static web route (HttpServer AddRoute) now serves from ModLoader\Plugins\<plugin>\<folder> under the game's Binaries\Win64 folder. Since the loader moved into ModLoader\, the route looked in ModLoader\ModLoader\Plugins and served nothing.
- The Browse tab can now install a plugin. A mod in the mod index that lists a download has an Install button. One click downloads the mod from its GitHub release (https only, and only from GitHub's release download addresses), checks its size and SHA-256 against the mod list before anything is written, then writes the plugin's DLL, with its .json for the auto-updater when the entry lists one, to ModLoader\Plugins and starts it right away when it can; if it can't, the card says "Installed. It will be on after you restart the game." Install never replaces a file: if the DLL or .json is already in Plugins it stops and names the file, and a download that fails or doesn't match leaves nothing behind. One install runs at a time. Install is greyed out, with the reason on hover and under the card, when the mod needs another mod that isn't installed or is disabled ("MainMap needs MiniMap. Install MiniMap first."), Vortex manages the mod ("Vortex manages this mod. Install it in Vortex."), it needs a newer ModLoader, or another install is running. Install works only from a signed mod list: the built-in one, or a list you set with modloader.ini [AutoUpdate] ModIndexUrl that serves a signed file; if the list can't be loaded the tab says why ("The mod list isn't published yet.", "The mod list server answered with an error (HTTP NNN).", "The mod list is larger than allowed." for a download over 1 MB, "The mod list is too large to read." for a list over 256 KB); a list that isn't signed says so ("This list isn't signed. It comes from the address you set yourself. Nothing can be installed from it.") and installs nothing, though its cards can still be read. ModLoader.log gets an [Install] line for each step. A search box filters the list by words from a mod's name, author or description, in any order; a word of 3 letters or more also matches a name with those letters in order, so "minmap" finds MiniMap. A mod index entry can now say "server_only": true (optional, older loaders ignore it); the card then shows "(Server)" after the author, with the tooltip "Runs on a dedicated server", and never has an Install button, even if the entry lists a download (the index check refuses that combination). mod-index/README.md describes the install fields and server_only, and mod-index/GETTING-LISTED.md has the steps for an author
- The Browse tab can now turn plugins off, uninstall them and bring them back. It lists your installed plugins along with the ones in the mod index. Disable keeps a plugin off, also after a restart, and Enable turns it back on. Uninstall asks first, then moves the plugin's files (DLL, plus its .json and .pdb if it has them) into ModLoader\Removed; your settings, save data and subfolders stay, and Restore on the same card brings it back as it was, so a plugin you had disabled stays disabled. Restore is refused if the same plugin is already installed under another file name ("A copy is already installed as X.dll, so the old one stays in ModLoader\Removed."). If a plugin can't stop or start right away, the change happens after you restart the game. A plugin Vortex installed is uninstalled in Vortex, though you can still disable it here. The tab warns you if another installed, enabled plugin needs the one you're disabling or uninstalling, but only for what the mod index lists. A Preload plugin has a card only if the index names it.
- A plugin can now use a newer loader feature only when the running loader has it, instead of declaring the newer level and being refused by older loaders (plugin interface v80). The plugin sets PLUGIN_NEEDS_INTERFACE to the oldest loader it runs on and PLUGIN_OPTIONAL_INTERFACE to the newest level it may use, and puts PLUGIN_EXPORT_HOST_INFO() in one source file. A loader with interface 80 calls the plugin's optional PluginSetHostInfo export once, after GetPluginInfo and before any other code of the plugin runs (OnPluginLoadHooks, PluginInit), with its own interface level; a fault in it is handled like a fault in PluginInit, and a plugin without the export loads as before. The SDK header then offers PluginHostHas(n) and one accessor per newer member (PluginOptRegistry, PluginOptServerAddress, PluginOptImages, PluginOptDL_AddTexturedTriangles, PluginOptHostRules) that returns nullptr on a loader without it, so the feature is simply off. A loader below 80 never calls the export, so the plugin keeps working there with the optional features off.
- The Browse tab now shows a plugin's README in the mod loader window. A card whose index entry has a readme_url gets a README button that opens the author's README from their GitHub repo, with its headings, paragraphs, lists, tables, bold, code, links and pictures; very large tables are cut short, emoji and some other symbols are left out or written with plain characters, and SVG pictures and scripts are not shown or run. Pictures load only from GitHub hosts, up to 8 per README and 2 MB each, only GitHub and Nexus Mods links can be clicked and they open in the browser, nothing is saved to disk, and leaving the page frees the pictures. mod-index/README.md explains readme_url
- A new Browse tab in the mod loader window lists plugins from the mod index: each plugin is a card with its name, version and author, its summary, a line with the plugin's state when you have it installed, the ModLoader version it was last tried on and an Open page button that opens its page in the browser. The list is downloaded once, on a background thread, the first time the tab is opened, and kept in memory; a failed download shows one line and a Retry button, and the window is never held up by it. Only a page address on nexusmods.com or github.com (https, no port) is opened, and only when the button is clicked. An entry the loader cannot read is left out, and a list of more than 200 plugins is cut with a note. The list is a signed file: the loader checks the signature before it reads any entry, keeps the last good copy and shows it when a download fails, and refuses a file that fails the check or is older than the copy. modloader.ini [AutoUpdate] ModIndexUrl names another https address instead; the built-in address takes only a verified signed file, an address you set may serve a signed file or a plain index file. The index format is described in mod-index/README.md. The tab sits before About, so the number keys 1 to 5 still open Plugins, Config, Settings, Logging and Theme
- A plugin the mod loader cannot run because it was built for a newer plugin interface now says which mod loader to get. The plugin list and the console show "Needs ModLoader v1.28.0 or newer" when the latest release supports it, "Built for a ModLoader newer than the latest release" when it does not, and "Needs a newer ModLoader" when the loader could not read the latest release. When the latest release is known, ModLoader.log gets one line at the refusal, "[AutoUpdate] <plugin> (interface N): " and the same sentence, and the existing "Plugin interface version N is newer than this loader supports" line is unchanged. The release manifests (manifest-client.json, manifest-server.json) now also carry interface_version_min and interface_version_max, the plugin interface range that release accepts; older loaders ignore the two fields, and a manifest without them gives the plain wording.
- A plugin can now read the project's signed plugin catalog (plugin interface v80: hooks->Registry->GetFeatureCatalog(buf, size)): the list of plugins and the features they declare, with the game builds each feature is off in. The project's CI publishes the catalog next to the version object map, signed with the same key. The mod loader fetches it once per launch, checks the signature, keeps the last good copy on disk and refuses an older file, so the text is a snapshot of the last verified file and may be older than the plugins that are running (GetDeclaredFeatures is the live list). It uses the same text convention as GetDeclaredFeatures: it returns the full length and cuts to the buffer like snprintf, and a null buffer with size 0 measures. -1 means there is no verified catalog: until a catalog is published, on a first launch that could not fetch it, and always on a dedicated server for now. A plugin that uses it declares interface 80, so an older loader refuses it. Call it from Tick, not from a render callback.
- A client plugin can now read the address of the server it is connected to (plugin interface v80: hooks->Network->GetServerAddress(buf, size)), so it can pin a secret it was paired with to that server. The text is the address the player's own connection reports, as lower-case UTF-8, for example 203.0.113.7:7780; a relay or peer route may print something else, so a plugin pins the text as it is and treats a changed text as a different server. It returns the full length and cuts to the buffer like snprintf, a null buffer with size 0 measures, and -1 means there is no address to give: a dedicated server or generic build, no connection to a server yet (main menu, travelling, single player, the host of a listen server), a game build where the loader could not place the engine call, a call from a thread other than the game thread, or an address the engine reports as invalid. The loader never logs the address. A plugin that uses it declares interface 80, so an older loader refuses it. Call it from Tick, once IsServerReady() is true, not from PluginInit, a render callback or a worker thread. The loader finds the engine call by its byte pattern, backed by version object map rows for CL-129402 and CL-130045; on a build where neither finds it, the call returns -1.
- A plugin can now list the features every running plugin declares (plugin interface v80: hooks->Registry->GetDeclaredFeatures(buf, size)). The text is tab-separated: one row per running plugin and one per feature with its id, whether it is on in this game build, and its title, sorted by plugin and id. It returns the full length and cuts to the buffer like snprintf, a null buffer with size 0 measures, and -1 means the plugins have not finished starting yet. The loader writes the same text to ModLoader\Logs\declared-features.v1.txt once the plugins have started and again after each reload; the file is a snapshot, the function is always live. Plugins that load in the preload stage are not listed. Call it from Tick, not from PluginInit (it returns -1 there during startup) and not from a render callback.
- A plugin can now ask the loader whether another plugin is loaded and enabled, and which version it is (plugin interface v80: hooks->Registry->GetPluginVersion(name, out, cap)). A plugin that is disabled, unloaded, being reloaded or switched off after a crash reads as not loaded, and a buffer too small for the whole version text gives false and an empty result. A plugin that uses it declares interface 80, so an older loader refuses it. Call it from Tick, not from a render callback.
- If you use Vortex, the mod loader can now remind you when an update it made, to a plugin or to itself, replaced a file Vortex installed, in the Plugins Updated window or the mod loader update box, and in the log. Nothing changes if Vortex did not install the files. The reminder reads: Vortex manages these files. When Vortex shows External Changes, choose "Save change (use deployed file)" for each updated mod, then Confirm. Revert would undo this update.
- For plugin authors: the plugin SDK's main branch now changes only when a mod loader release comes out, so a plugin built from it matches a released loader. Header changes that are not released yet go to the SDK's next branch.
