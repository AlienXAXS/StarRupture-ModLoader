- A new Browse tab in the mod loader window lists plugins from the mod index: each plugin is a card with its name, version and author, its summary, and a line with an Installed marker when a plugin of that name is loaded, the ModLoader version it was last tried on and an Open page button that opens its page in the browser. The list is downloaded once, on a background thread, the first time the tab is opened, and kept in memory; a failed download shows one line and a Retry button, and the window is never held up by it. Only a page address on nexusmods.com or github.com (https, no port) is opened, and only when the button is clicked. An entry the loader cannot read is left out, and a list of more than 200 plugins is cut with a note. The tab does not download or install anything. The list is a signed file: the loader checks the signature before it reads any entry, keeps the last good copy and shows it when a download fails, and refuses a file that fails the check or is older than the copy. modloader.ini [AutoUpdate] ModIndexUrl names another https address instead; the built-in address takes only a verified signed file, an address you set may serve a signed file or a plain index file. The index format is described in mod-index/README.md. The tab sits before About, so the number keys 1 to 5 still open Plugins, Config, Settings, Logging and Theme
- A plugin the mod loader cannot run because it was built for a newer plugin interface now says which mod loader to get. The plugin list and the console show "Needs ModLoader v1.28.0 or newer" when the latest release supports it, "Built for a ModLoader newer than the latest release" when it does not, and "Needs a newer ModLoader" when the loader could not read the latest release. When the latest release is known, ModLoader.log gets one line at the refusal, "[AutoUpdate] <plugin> (interface N): " and the same sentence, and the existing "Plugin interface version N is newer than this loader supports" line is unchanged. The release manifests (manifest-client.json, manifest-server.json) now also carry interface_version_min and interface_version_max, the plugin interface range that release accepts; older loaders ignore the two fields, and a manifest without them gives the plain wording.
- A plugin can now read the project's signed plugin catalog (plugin interface v80: hooks->Registry->GetFeatureCatalog(buf, size)): the list of plugins and the features they declare, with the game builds each feature is off in. The project's CI publishes the catalog next to the version object map, signed with the same key. The mod loader fetches it once per launch, checks the signature, keeps the last good copy on disk and refuses an older file, so the text is a snapshot of the last verified file and may be older than the plugins that are running (GetDeclaredFeatures is the live list). It uses the same text convention as GetDeclaredFeatures: it returns the full length and cuts to the buffer like snprintf, and a null buffer with size 0 measures. -1 means there is no verified catalog: until a catalog is published, on a first launch that could not fetch it, and always on a dedicated server for now. A plugin that uses it declares interface 80, so an older loader refuses it. Call it from Tick, not from a render callback.
- A client plugin can now read the address of the server it is connected to (plugin interface v80: hooks->Network->GetServerAddress(buf, size)), so it can pin a secret it was paired with to that server. The text is the address the player's own connection reports, as lower-case UTF-8, for example 203.0.113.7:7780; a relay or peer route may print something else, so a plugin pins the text as it is and treats a changed text as a different server. It returns the full length and cuts to the buffer like snprintf, a null buffer with size 0 measures, and -1 means there is no address to give: a dedicated server or generic build, no connection to a server yet (main menu, travelling, single player, the host of a listen server), a game build where the loader could not place the engine call, a call from a thread other than the game thread, or an address the engine reports as invalid. The loader never logs the address. A plugin that uses it declares interface 80, so an older loader refuses it. Call it from Tick, once IsServerReady() is true, not from PluginInit, a render callback or a worker thread. The loader finds the engine call by its byte pattern, backed by version object map rows for CL-129402 and CL-130045; on a build where neither finds it, the call returns -1.
- A plugin can now list the features every running plugin declares (plugin interface v80: hooks->Registry->GetDeclaredFeatures(buf, size)). The text is tab-separated: one row per running plugin and one per feature with its id, whether it is on in this game build, and its title, sorted by plugin and id. It returns the full length and cuts to the buffer like snprintf, a null buffer with size 0 measures, and -1 means the plugins have not finished starting yet. The loader writes the same text to ModLoader\Logs\declared-features.v1.txt once the plugins have started and again after each reload; the file is a snapshot, the function is always live. Plugins that load in the preload stage are not listed. Call it from Tick, not from PluginInit (it returns -1 there during startup) and not from a render callback.
- A plugin can now ask the loader whether another plugin is loaded and enabled, and which version it is (plugin interface v80: hooks->Registry->GetPluginVersion(name, out, cap)). A plugin that is disabled, unloaded, being reloaded or switched off after a crash reads as not loaded, and a buffer too small for the whole version text gives false and an empty result. A plugin that uses it declares interface 80, so an older loader refuses it. Call it from Tick, not from a render callback.
- A server's mod loader now writes one warning to ModLoader.log when a player joins on a different game build, for example "Player 'X' runs game build CL-130045, this server runs CL-127004. Expect garbled data or disconnects until they use the matching build." The player's mod loader adds its game build number and exe stamp to the feature list it already sends (a $game record in $ML:feat; older mod loaders skip it, and a feature list without it is never a mismatch). Nothing is refused or removed, a build that is not known on either side is never reported, and plugins do not see the new field. Only the server's loader checks this.
- A player now sees the server's admin prompt: a window with a text box and the buttons Send and Not me, which shows the server's line after each try and its last line before it closes. The player types the claim code, or chooses "not me" (the X in the window's title bar does the same). A window the player dismissed is not shown again for 60 seconds. The player's loader checks a code before sending it (1 to 64 characters, no control characters) and sends one answer per half second at most. Nothing is sent unless the server proved it reads host rules, the code is never logged or kept after it is sent, a malformed prompt message from the server is dropped with one warning per connection, and leaving the server closes and clears the prompt. Player builds only; the server build does not contain this.
- A server plugin can now ask a player for an admin code (interface 79: IPluginHostRules.AskAdmin, AdminMessage, RegisterOnAdminAnswer, UnregisterOnAdminAnswer). AskAdmin opens a prompt for a player whose loader reported its features; AdminMessage shows a line in it, and with close set the prompt closes after the line. The code the player types, or "not me", reaches the registered callback from the tick; the loader does not check the code, never logs it, clears its own queued copy once the callbacks have run (copies in network buffers and the plugin's own copy are out of its reach), drops answers from a player that was not asked and allows one answer per 500 ms per player. The loader sets no limit on tries, so a plugin counts wrong codes itself and closes the prompt after a few. Only the server's loader does this; on any other process the calls warn once and do nothing.
- A server plugin can now ask for a minimum ModLoader version and a minimum version per mod (interface 79: IPluginHostRules.SetVersionMinimums, RegisterOnClientBelowMinimum, UnregisterOnClientBelowMinimum). The minimums are text, one per line: loader=1.27.0, Plugin=0.11.0, Plugin=wire (the player's copy must be one the mod wire check accepts); a bad text is refused and the call says which line. When a player's loader or mod is below, the plugin is called once per join with the player and one line of plain words to show them, such as "This server needs RuptureTimer 0.11.0 or newer (you have 0.9.2). Update RuptureTimer, or remove it, and join again." The loader never removes anyone; the server plugin does that and can exempt admins. Players with no mod loader are never checked, a dev build or a version the loader cannot read is never below, a text after - or + in a version is ignored when comparing (1.26.0-dev.3 is below 1.27.0), and a loader too old to report its version counts as below a loader minimum after 30 seconds, not counting time the game stalled for more than 2 seconds. Only the server's loader does this; on any other process the calls warn once and do nothing.
- A server plugin can read what one player's loader reported (interface 79: IPluginHostRules.GetClientFeatures): the loader build and plugin interface version, then one Plugin.feature=on|off line per feature. It returns -1 when the player has no report (an older loader, or no mod loader).
- A server plugin can now set the rules a server sends to its players, for everyone or for one player at a time (interface 79: IPluginHostRules, reached as hooks->HostRules, with SetRules, SetRulesForConnection, ClearConnection and RegisterOnClientFeatures). The rules are written as text, one per line: default=allow|deny, message=<text>, Plugin.feature=allow|deny, Plugin.*=allow|deny; a bad text is refused and the call says which line. A rule set for one player replaces the server-wide set for that player whole, and the features hostoff list and features hostmessage text apply only to players with no set of their own. The rules reach every player who sent a feature list at once, and a plugin is told when a player's feature list arrives (at most once per second per player). A rule splits at the first dot, so a plugin whose own name has a dot cannot be named in the text, and the message= line goes to the player's ModLoader.log. A player's own set ends when the player leaves or the world ends. Only the server's loader does this; on any other process the calls warn once and do nothing.
- A server now sends its feature deny list to the players on it. When a player's mod loader has sent its feature list, the server sends its deny list, and the player's loader switches those features off within a moment, also for a plugin that loads or reloads later and for features a "*" or default row names. The list is sent again when it changes (features hostoff, features hostclear) and when the player's plugins change. features hostmessage <text> sets a text that goes with the list and is written to the player's ModLoader.log; an empty text clears it. The features command now also shows what the server you joined turned off and its message. A deny list a player set on their own machine with features hostoff is kept apart from the server's: leaving the server gives the server's features back and leaves the player's own. A player on a server whose mod loader is older gets no list, and ModLoader.log says once "No host rules (the server's mod loader is older)".
- A server can now turn a plugin feature off for the players on it. The loader keeps a deny list of plugin and feature pairs; a feature on the list is off whatever the game build allows, and it comes back when it leaves the list (a feature the game build turned off stays off either way). The plugin's own flag for the feature is set off, also when the plugin is reloaded or loads later. The plugin's config page greys the feature with "<feature> is off: turned off by this server", the plugin shows as Loaded (1 off), hookfailures lists it as "[feature off]" with the reason "turned off by this server", and ModLoader.log writes "feature turned off by this server" and "turned back on". No pop-up opens. The new console command features lists every feature a loaded plugin declared with its state (on, off: build, off: server) and the deny list; features hostoff <plugin> <id> adds one to the list and features hostclear empties it. The list is kept in memory and is empty at every start
- On the dedicated server, the HTTP method of a request now reaches plugins correctly, so web panels of server plugins can POST again. Before, every request reached plugins as an unknown method and a plugin that only accepts POST rejected its own panel. The method comes from the version object map row for the server game build (CL-127004); a server build without that row keeps the old behaviour and ModLoader.log says so.
- A message with a percent sign in it, such as a web address a plugin or the server logged, no longer risks a fault or a stuck log in the mod loader's log; the percent signs are now written as they are
- When a game update changed some of the game classes the mod loader's start check reads, but none that every plugin depends on, a plugin that does not take its game data from the version object map was refused. It is now still loaded if it names the game build it was compiled for and that is the build running, since its game data is that build's. If a class every plugin depends on changed, or the game's ProcessEvent moved, all plugins still stay off. A plugin that names no build or another build, and has not moved to the version map, is refused as before
- The mod loader's client build now takes its game classes from the CL-130045 game files and still runs on CL-127004 with the same files. The version object map keeps the rows for both builds, and the two members that sit at a different place on the two builds (a crafter's crafting component and the enviro wave timer's actor) are read per build, so a CL-127004 game is not mistaken for a changed layout. The dedicated server is unchanged and stays on CL-127004
- The dedicated server's mod loader now supports the version object map, as the client's does. It carries built-in rows for the one server game build it was written for (CL-127004): function addresses, the game's data globals, and member offsets and struct sizes read from the server's own game files. A plugin that asks for a version map key, member or struct size gets the row on that exe, matched by its game build and the exe's own stamp and size, and the server hands plugins the same Game-SDK globals as the client (GObjects, GNames, FName::AppendString and GWorld). It can also download, check and keep its own signed server version map file (version-map-server.v1.txt, kept as ModLoader\version-map-server.v1.cache), so a newer server game build can get its rows from the file with no loader update. A client never reads the server's file and a server never reads the client's. The Server Release build carries the file's address; a server build made without one fetches nothing and says so in ModLoader.log. The file's rows are used only when the game build number, the exe's time stamp and its image size all match a build line in it, and the built-in rows win on the exe they were measured on. [AutoUpdate] Enabled=0 stops the server's request too. On a server game build that only the file lists, if the loader's own entries or the game globals cannot all be found, the server starts with no plugins and no dialog, and ModLoader.log says which were missing. A server game build that no list has still stops the loader. ModLoader.log now prints one line per build in a fetched file: whether it is this exe or another, its row count, and whether it is identical to the loader's own, differs, was added or was refused
- When the game does not finish starting within the mod loader's wait on a game build the mod loader was not made for, the mod loader's message now says so, instead of saying the game layout changed: "The game did not finish starting within 120 seconds, so the ModLoader could not check it." It adds that the game may be stuck on a message box of its own, or its files may be damaged (verify the game files in Steam). ModLoader.log says the same, and its "Stage 2 complete" line no longer says "engine ready" when the wait ran out. Plugins stay off for that session, as before; a layout change that was really found keeps its own message
- The wait for the game to finish starting is now a true 2 minute limit. Before, every window message that reached the mod loader's startup thread restarted the 2 minutes, so the wait could run much longer (158 seconds in one report)
- The dedicated server's mod loader now runs the same start check on the game's classes as the client, against a table made from the server's own game files. If a class the loader reads, or one that plugins keep compiled in, is laid out differently on the running server game build, the server starts with no plugins and ModLoader.log lists the changed classes (the [LayoutCheck] lines) and says plugins are switched off for the session. A class that only a version object map key names does not switch plugins off: a plugin that keeps its layout compiled in is refused, one that takes it from the version object map is not. On a server game build other than CL-127004, a check that could not run keeps the plugins off and ModLoader.log says so. The compatibility report stays client-only
- The mod loader's start check now has a layout table for each game build it supports (CL-127004 and CL-130045), and a game on either build is checked against its own. A game build with no table of its own is checked against the newest one, and the ModLoader.log line says so, ending "game build 140000, no table of its own: the newest is used". The compatibility report's sdkCL is the CL of the table that was used
- The mod loader's start check now covers more of the game's classes: 259 for CL-130045 and 255 for CL-127004, where it was 159 for both. Each game build is still checked against its own table, so this adds checks without making a CL-127004 game look like a changed layout
- When a fault happens inside the game's world-end call (UWorld::EndPlay), the mod loader still swallows it as before, and now writes three lines to ModLoader.log instead of one: the exception code with the fault address as module and offset (and what an access violation touched), the registers, and a short call stack as module and offset. Nothing changes when no fault happens
- Plugin data now crosses between a server and a player who run different versions of the same plugin, when the plugin says those versions are compatible. Before, a plugin's data passed only between identical versions, so updating the plugin on one side stopped it with no message. A plugin says so by exporting the optional GetPluginWireInfo (a number for its data format, and a list of other versions it works with); the rule applies in both directions, so a player on a version that is not known to match no longer sends that plugin's data to the server either; it needs no new plugin interface version, and a plugin that says nothing keeps the identical-version rule. When two versions cannot exchange data, ModLoader.log on the server and on the player's PC each now have one line naming the plugin and both versions ("Wire format not known to match, plugin data will not be exchanged"), and when two different versions are accepted one line says why, so a player who is missing a plugin's data can look for them. Older mod loaders ignore the extra information, so an older player can still join a newer server. A server whose mod loader is older than this still needs identical plugin versions and cannot be told otherwise; the player's ModLoader.log then says so once, when a plugin there uses the network channel.
